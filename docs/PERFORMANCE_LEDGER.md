### 3.1b Rerank stage (post-BBF, double-precision insertion sort) — NEW ATTACK SURFACE

Onda 22 Phase 1 instrumentation (INSTR-gated `rerankCandidates`/`rerankDoubleCalls`/`rerankInsertions` + `poolI16SumLog` + `peekSumFinalI16`) over 54 100 deterministic queries surfaced the rerank stage as the next data-driven target:

- pool size: mean **40** / p50 40 / p99 60 / max 76 (smaller than brief assumption ~100 — Onda 11 BBF already tightened collection)
- dedup ratio: **12.09 %** agg / p99 17.24 % → weak lever (most loop iterations are real work, not skips)
- **`earlyExit.potential` = 86.20 % agg / p99 91.66 %** (1.9 M of 2.2 M candidates have `i16Sum > peekSumFinalI16` — the soundness ceiling of H2)
- insertion-sort hits: mean 13 / p99 20 (37 % of double calls trigger an insert; H6 marginal)
- BenchRerank HotSpot baseline: **30.24 ns/call** median, dominated by Math.round + ×10000 + ÷10000 of the query lane per call

**WINNERS**:
- (Onda 22 H1, 2026-05-21) **Hoist `round4(query)` out of rerank loop.** Pre-compute `queryRound4[14]` once per query in `prepareSearch`; new `sqDistDoubleLikeC(double[], short[])` overload uses it. BenchRerank **30.24 → 13.45 ns/call = −55.5 %** (better than predicted −37 %; Math.round dominates more than estimated). 54 100 ExactAgree 0-div; zero-alloc preserved; VisitsReplay rerank counters IDENTICAL (algorithm unchanged by construction). Per-query savings ≈ 588 ns mean / 923 ns p99 — small absolute (rerank is <1 % of Mac Mini p99 ~35 ms; tail is CFS scheduling / mmap eviction) but locks bit-identical baseline for H2.
- (Onda 22 H2, 2026-05-21) **Early-exit por i16-5th double bound argument no rerank loop.** `KdScratch.poolI16Sum[POOL_CAP]` promoted to UNCONDITIONAL production field (256 KB); `KdTree.poolRecord` writes i16Sum unconditionally; `KdTree.search` skips candidates with `poolI16Sum[p] > peekSumFinalI16` antes do double kernel. **Soundness**: o i16-5th double bound argument (documentado em `poolRecord:336-343`) prova que qualquer nó com i16Sum > final-5th's i16Sum tem doubleSum > final-5th's doubleSum por ≥ ~1e-8 (gap `1/1e8 ≫ ~2e-14` round-off slack); como o pool tem ≥5 entries with i16Sum ≤ final-5th (i.e., ≥5 candidatos com doubleSum menor), o nó podado não pode entrar no top-5 double. **Bug pré-commit**: `heapsortByOrig` precisou virar 3-arg (sortar `poolI16Sum` paralelo a `pTree`/`pOrig`); sem isso o índice `[p]` da i16Sum ficava desalinhado dos candidatos sortados ⇒ 27 416 mismatches em G2 ExactAgree (50.7 % failure rate). Pego e corrigido antes do commit. Após fix: **rerank.double mean 35→5 (−86 %)**, h2.skip.ratio agg 75.69 % (abaixo do teto earlyExit 86.20 % por overlap com dedup 12 %); BenchSearch (HotSpot end-to-end) 16,999 → 16,235 ns/search = **−764 ns/search (−4.5 %)**. ExactAgree 0/54 100 mismatches; AllocCheckKd 0.00 B/q; VisitsReplay determinístico.

**OPEN** (queued):
- (research) HW-prefetch hint for the rerank loop's `poolI16Sum[p+1]` access — but pool already fits in L1d so likely no-op.

**FALSIFIED for this stage**:
- H3 (cast-trick `(long)(x*10000+0.5)/10000.0` replacing `Math.round`) — `Math.round` is half-up, C `round()` is half-away-from-zero; differs for `x < 0` (sentinela `-1` in lanes 5/6 when `last_transaction = null`). H1 dominates without this risk.
- H4 (insertion sort replacing heapsort on pool by origId) — heapsort O(n log n) ≈ 280 comps already beats insertion O(n²/2) ≈ 800 for typical n ≈ 40.
- **H6 (branch-free top-5 insertion sort, 2026-05-21)** — implemented (5-slot specialized, 5× ternary assignments per slot via `ltJ = d < dists[j]`, sound by construction `lt0 ⇒ lt1 ⇒ ... ⇒ lt4`), G1+G2+G3 all green (0/54 100 mismatches, 0 B/q). Falsified by BenchSearch 9-trial test: H6 mean **16 339 ns/search** vs post-revert mean **15 446** = **+6.4 % regress**; H6 spread 10.5 % vs branchful spread 2.9 % ⇒ also noisier. Insight: pós-H2 toda chamada double resulta em inserção (rerank.ins ≈ rerank.double = 5), com insertion-position distribution previsível, então branch predictor já é ótimo; branchless paga sempre 5 cmov vs branchful média ~3 com break + sai cedo. Original 9-trial data: H6 trials = 17283, 15794, 17321, 16432, 15677, 17227, 17143, 16188, 15986 (sorted 15677, 15794, 15986, 16188, 16432, 17143, 17227, 17283, 17321); branchful 3-trial = 15670, 15221, 15446 (sorted 15221, 15446, 15670). Reverted (KdTree.java with FALSIFIED comment block pointing here).
