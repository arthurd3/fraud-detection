# k6

**Categoria**: Load testing / benchmark de APIs
**Versão usada na Rinha**: v0.50+
**Decisão rápida**: ferramenta oficial da Rinha — não há decisão

---

## O que é

k6 é uma ferramenta open source de **load testing** e **performance testing**. Você escreve scripts em JavaScript (ES6+), o k6 executa em runtime Go (sem precisar de Node.js) e gera estatísticas detalhadas de latência, throughput, erros.

Mantida pela Grafana Labs (que adquiriu a empresa fundadora). Foco em developer experience: scripts em JS, output rico, integração com observability stack.

## Objetivo geral

Substituir ferramentas mais antigas (JMeter UI-baseado, ab — Apache Bench) com:

1. **Scripts em código** (JS) — versionável, reusável, lógica complexa fácil.
2. **Output amigável** (terminal + JSON) — métricas detalhadas.
3. **Cenários sofisticados**: rampa de RPS, virtual users (VUs), pacing.
4. **Performance**: roda 10k+ RPS em uma máquina.

## Pra que vamos usar no projeto

`rinha-de-backend-2026/test/test.js` é o script oficial da Rinha. Roda contra HAProxy (porta 9999) com:

- Cenário `ramping-arrival-rate`: 1 → 900 RPS em 120s.
- 54.100 payloads pré-rotulados em `test/test-data.json`.
- Asserções: response 200, fields `approved` e `fraud_score` corretos.
- Output: `test/results.json` com estatísticas + `final_score` da Rinha.

Comando: `k6 run rinha-de-backend-2026/test/test.js`.

## Como funciona (em profundidade)

### Arquitetura

```
[script JS]  →  [k6 binary Go]  →  [VU pool]  →  [HTTP requests] → [API]
                       ↓
              [stats engine]
                       ↓
              [output: terminal + JSON]
```

VU = Virtual User = goroutine simulando um cliente. k6 pode rodar milhares por máquina.

### Estrutura de um script k6

```javascript
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  scenarios: {
    rinha: {
      executor: 'ramping-arrival-rate',
      startRate: 1,
      timeUnit: '1s',
      preAllocatedVUs: 100,
      maxVUs: 250,
      stages: [
        { target: 900, duration: '120s' },
      ],
    },
  },
};

const data = JSON.parse(open('./test-data.json'));
let i = 0;

export default function () {
  const payload = data[i++ % data.length];
  const res = http.post('http://localhost:9999/fraud-score',
    JSON.stringify(payload.input),
    { headers: { 'Content-Type': 'application/json' } });
  
  check(res, {
    'status 200': (r) => r.status === 200,
    'approved correto': (r) => JSON.parse(r.body).approved === payload.expected_approved,
  });
}
```

### Executors

| Executor | Como funciona |
|---|---|
| `constant-arrival-rate` | RPS fixo (independente de VU completion) |
| `ramping-arrival-rate` | RPS muda em stages (Rinha usa este) |
| `constant-vus` | N VUs constantes |
| `ramping-vus` | N VUs varia em stages |
| `per-vu-iterations` | cada VU faz N iterações |
| `shared-iterations` | total de iterações dividido entre VUs |

`arrival-rate` é melhor para benchmark **realista** porque mantém o RPS mesmo se latência cresce (não fica esperando VU livre).

### Métricas

k6 emite:
- `http_req_duration` — latência por request (p50, p95, p99, p999, max).
- `http_req_failed` — taxa de falhas (status ≥ 400).
- `http_reqs` — total de requests, RPS médio.
- `vus` / `vus_max` — VUs ativos.
- `iteration_duration` — tempo de uma iteração (= 1 request na Rinha).
- `data_received` / `data_sent` — bytes.

Asserções (`check`) viram métricas: `checks` (passou) e `checks_failed`.

### Output

Terminal padrão:
```
checks.........................: 99.99% ✓ 53996  ✗ 4
http_req_duration..............: avg=2.3ms min=0.5ms med=1.8ms max=78ms p(95)=4.2ms p(99)=8.7ms
http_reqs......................: 54000  450/s
```

JSON detalhado: `--out json=results.json`.

### Thresholds

```javascript
export const options = {
  thresholds: {
    'http_req_duration': ['p(99)<2000'],  // p99 < 2s
    'http_req_failed': ['rate<0.15'],     // <15% falhas
  },
};
```

Quando threshold falha, k6 retorna exit code != 0 (útil em CI).

### Pacing

Para evitar bombardear o servidor:
```javascript
sleep(0.1);  // 100ms entre iterações
```

Na Rinha, sem sleep — `arrival-rate` controla RPS.

## Exemplo de uso

```bash
# Run básico
k6 run script.js

# Com env var
k6 run -e BASE_URL=http://localhost:9999 script.js

# Output JSON
k6 run --out json=results.json script.js

# Run da Rinha
cd /home/arthurd3/Desktop/RINHA-BECK-END/rinha-de-backend-2026/
k6 run test/test.js

# Ler score
cat test/results.json | jq '.scoring.final_score'

# Subir RPS de teste
k6 run --vus 200 --duration 30s script.js
```

## Tecnologias parecidas (alternativas)

| Tecnologia | Vantagem | Desvantagem | Quando preferir |
|---|---|---|---|
| **wrk** (C) | Performance bruta máxima (1M+ RPS) | Lua scripting limitado, sem asserções ricas | Microbench HTTP cru |
| **Apache Bench (ab)** | Mais simples, built-in | Cenários simples, sem rampa | Sanity check rápido |
| **Vegeta** (Go) | CLI simples, alto throughput | Menos flexível em cenários | Steady-state RPS test |
| **JMeter** (Java) | Maduro, GUI rica, plugins | Pesado, scripts em XML, menos developer-friendly | Equipes não-dev fazendo perf |
| **Gatling** (Scala) | Reports HTML lindos, async | Aprendizado de Scala/DSL | Apps Scala/Java enterprise |
| **Locust** (Python) | Scripts em Python | Throughput menor que k6/wrk | Equipes Python |
| **Tsung** (Erlang) | Distribuído, multi-protocolo | Setup complexo | Testes massivos distribuídos |
| **bombardier** (Go) | Mais simples que vegeta | Cenários limitados | Smoke tests |

Na Rinha: **k6 é mandatório** — script oficial é `test.js`. Não há alternativa.

## Pegadinhas conhecidas

1. **VU pool insuficiente**: se `maxVUs` < demanda pico, k6 dropa requests. `arrival-rate` avisa.
2. **`open()` é só no init context**: scripts não podem ler arquivos durante execução.
3. **Memória**: 250 VUs × ~5 MB = ~1.25 GB. Setup com mais VUs precisa monitorar RSS do k6.
4. **JSON output gigante**: rodando 60s @ 900 RPS = 54k linhas. Use `summary` em vez de full json se só quiser estatísticas.
5. **Localhost vs container**: rodando k6 localhost contra Docker, considerar latência de bridge (~10-50 µs).
6. **Time sync**: dois processos diferentes leem clock diferente. Para microsec-level, considerar.
7. **`http.batch()`**: paraleliza N requests numa iteração. Útil mas confunde stats (1 iter = N reqs).
8. **`check()` falha não aborta**: registra falha mas continua. Use `fail()` para abortar.
9. **Variáveis de ambiente**: `__ENV.BASE_URL` (não `process.env`).
10. **Thresholds avaliados no fim**: não param o teste, só decidem exit code.
