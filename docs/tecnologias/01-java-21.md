## O que é

Java é uma linguagem de programação **estaticamente tipada**, **orientada a objetos**, com sintaxe inspirada em C/C++. Compila para **bytecode** (`.class`) que roda em uma máquina virtual (a JVM — Java Virtual Machine). É uma das plataformas mais maduras do mundo, com 30 anos de evolução, ecossistema gigantesco e suporte enterprise pesado.

Java 21 (Setembro 2023) é uma versão **LTS** (Long Term Support) da Oracle — recebe patches de segurança e bug fixes por **8+ anos**. É o sweet spot atual entre estabilidade e features modernas.

## Objetivo geral

A motivação original (1995) foi resolver o problema do "write once, run anywhere" — código compilado para bytecode roda em qualquer SO/arquitetura que tenha JVM. Hoje Java é dominante em backend enterprise (banking, telco, e-commerce), Big Data (Hadoop, Spark, Kafka), Android (até Kotlin tomar) e tooling (Maven, Jenkins).

## Pra que vamos usar no projeto

Linguagem principal de toda a `fraudAPI`. Escolhida porque:

1. **Vector API estável** (`jdk.incubator.vector`) — chave para SIMD do distance kernel.
2. **GraalVM Native Image maduro** em 21 — AOT compilation sem warmup.
3. **Virtual threads GA** (Project Loom) — disponível mesmo se não usarmos.
4. **Records, pattern matching, sealed classes** — features modernas que tornam código mais conciso.
5. **Familiaridade do time** + ferramental (Maven, IntelliJ, JFR).

Aplicação concreta: todos os arquivos `.java` em `fraudAPI/src/main/java/` rodam Java 21.

## Como funciona (em profundidade)

### Compilação em duas etapas

```
Foo.java  --(javac)-->  Foo.class (bytecode)  --(JVM JIT)-->  código nativo
```

1. **`javac`** compila `.java` para bytecode (linguagem da JVM).
2. **JVM** executa o bytecode em **2 modos**:
   - **Interpretado** (lento, sem otimizações).
   - **JIT-compiled** (rápido, código nativo cached em runtime).

### O JIT (Just-In-Time) do HotSpot

A JVM moderna chamada **HotSpot** tem 2 compiladores:
- **C1 (client)**: rápido, otimizações modestas (~5k execuções de um método para ativar).
- **C2 (server)**: lento, otimizações agressivas (inlining, escape analysis, vectorization). Ataca depois de ~10-100k execuções.

**Warmup**: até C2 entrar em ação, código roda 5-20× mais devagar. Em benchmarks curtos (~120s na Rinha), warmup come uma fatia significativa.

### Garbage Collector

Java tem GC automático. JVM 21 oferece:
- **Serial GC**: simples, pause longa (boa para Native Image).
- **Parallel GC**: throughput-oriented.
- **G1 GC** (default): balance, pause ~50ms target.
- **ZGC**: pause sub-millisegundo, mais memória.
- **Shenandoah** (Red Hat): similar ao ZGC.

Na Rinha, escolhemos **zero-allocation hot path** para nunca trigger GC durante uma request — strategy de §9 do `CONCEITOS.md`.

### Vector API (incubator)

`jdk.incubator.vector` permite escrever loops vetoriais que o compilador transforma em SIMD nativo (AVX2/AVX-512). Detalhes em [03-vector-api.md](03-vector-api.md) e `CONCEITOS.md` §5.

### Ecossistema de parsers JSON

Quando precisar de JSON em outro projeto:
- **Jackson** (mais popular) — tree model, streaming, data binding.
- **Gson** (Google) — similar, mais leve.
- **DSL-JSON** (codegen) — mais rápido que Jackson.
- **simdjson-java** — port do simdjson C++.
- **jsoniter** — focado em performance.

Na Rinha **rejeitamos todos** e fazemos parser hand-roll byte-array. Razão: schema fixo + zero-allocation + ~10 µs/request vs ~50-100 µs Jackson. (Detalhes em `RINHA_PLAN.md` §5.4.)

## Exemplo de uso

```java
// Hello World moderno (Java 21)
public class Main {
    public static void main(String[] args) {
        var greeting = "Hello, Rinha 2026!";  // type inference
        System.out.println(greeting);
    }
}
```

```bash
# Compilar
javac Main.java

# Executar
java Main
```

Para usar Vector API (preview):
```bash
javac --enable-preview --release 21 \
      --add-modules jdk.incubator.vector Main.java
java  --enable-preview --add-modules jdk.incubator.vector Main
```

## Tecnologias parecidas (alternativas)

| Linguagem | Vantagem principal | Desvantagem na Rinha | Quando preferir |
|---|---|---|---|
| **Kotlin** | Mais conciso, null-safety nativo | Runtime extra, sem benefício perf vs Java | App Android ou backend onde produtividade conta |
| **Scala** | Funcional, expressivo | Compilador lento, complexidade | Big Data (Spark) |
| **Rust** | Sem GC, zero-cost abstractions, SIMD trivial | Curva de aprendizado, ecossistema ANN/Native menor | Quando perf absoluta importa e você já é fluente |
| **Go** | Concorrência simples, deploy fácil, GC bom | Sem Vector API nativa, GC pause em hot path | Microsserviços com I/O dominante |
| **C / C++** | Controle total, perf máxima | Dev velocity baixa, manualmente gerenciar memória | Quando você já tem código C que reusa |
| **Zig** | Comptime poderoso, perf de C | Linguagem nova, ecossistema pequeno | Sistemas low-level |

Na Rinha 2026 escolhemos Java 21 por **time-to-market** com perf competitiva (graças a GraalVM + Vector API).

## Pegadinhas conhecidas

1. **`byte` é signed em Java** (-128..127). Quando precisar de `unsigned byte`: `b & 0xFF`. Critical para int8 quantization (ver `CONCEITOS.md` §4 e `RINHA_PLAN.md` §12.11).
2. **String é UTF-16 em memória** (2 bytes/char). Para parsing ASCII denso, prefira `byte[]` direto.
3. **`Double.parseDouble(String)` aloca**. Em hot path, parser manual em `byte[]`.
4. **Autoboxing oculto**: `List<Integer>`, `Map<Integer, V>`, `Optional<Long>` alocam wrappers. Use arrays primitivos (`int[]`, `long[]`) onde possível.
5. **Vector API é incubator**: pacote `jdk.incubator.vector` exige `--add-modules`. API pode mudar entre versões.
